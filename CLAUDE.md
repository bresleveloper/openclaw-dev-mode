### VPS Update Recipe

**By hand — there is no deploy script** (`dev-mode/vps-deploy.sh` is deleted; Ariel, 2026-11-11: "vps-deploy.sh delete"), so there is no automatic rollback either: back up `~/.openclaw` first and know the Revert steps before you start. The last committed copy of the script, whose wait loop rolled a healthy 11.3 gateway back, stays in `main`'s history (`64198b5542c`). The commands:
```
cd /opt/openclaw-dev-mode && systemctl --user stop openclaw-gateway && git config core.symlinks false && git checkout -- . 2>/dev/null; git pull --ff-only origin main && git config --unset core.symlinks && CI=true pnpm install --ignore-scripts && sh dev-mode/link-dist-plugin-deps.sh && ln -sfn /opt/openclaw-dev-mode node_modules/openclaw && systemctl --user start openclaw-gateway
```
- **Stop the gateway FIRST**: a running gateway restarts itself onto the new build seconds after the pull (`Installation replaced: running … build <old>; on-disk … build <new>`, then `Cannot find module …/dist/<old-chunk>.mjs` on shutdown: expected) and its first start would run the state upgrade before your backup; then `openclaw gateway stop` refuses without `--force` and a manual `gateway start` fails with "another OpenClaw process owns state-lifecycle" because systemd already restarted it.
- **Back up the WHOLE `~/.openclaw` BEFORE the first start** (the one-liner does not; gateway stopped, `cp -a ~/.openclaw <backup-dir>`): the previous build refuses upgraded DBs and a config that a newer version wrote (`src/config/future-version-guard.ts`), so a rollback restores `openclaw.json` together with the DBs. The first start runs the state upgrade (Key OpenClaw Internals) and can take many minutes (11.10: the upgrade took 3.6 min, and WhatsApp listened about 4 min after the first start).
- **No `openclaw` CLI call between the pull and the first start**: a CLI that opens the old state DB is refused with "Refusing a forward database schema migration" (the service-version gate, `src/state/openclaw-state-service-installation.ts`).
- Over SSH `systemctl --user` may need `export XDG_RUNTIME_DIR=/run/user/$(id -u)`. `git pull origin main` fetches only `main`, never an upgrade branch with upstream's history. `core.symlinks false` also covers pulls where a tracked symlink became a regular file (e.g. `CLAUDE.md`). `dev-mode/link-dist-plugin-deps.sh` recreates the `dist/extensions/<id>/node_modules` links the build makes on the build machine but never commits — without it `acpx` fails with "required dependencies are missing". Check out by commit and leave `main`'s upstream alone (`git checkout -B main origin/<branch>` re-points it; reset: `git branch -u origin/main main`).
- **Plugin dirs must be root-owned**: the loader refuses others (`blocked plugin candidate: suspicious ownership`, `src/plugins/discovery.ts:170`), so `chown -R root:root` any plugin files copied from Windows.
- **The gateway is up only after BOTH** the ready signal (the `gateway ready` log line OR `curl -fsS http://127.0.0.1:18789/readyz`) AND the `Listening for WhatsApp inbound messages` line (both in `~/.openclaw/logs/openclaw-YYYY-MM-DD.log` or journald) — never on the WhatsApp line alone (a scripted wait that broke on it rolled a healthy 11.3 gateway back, because `gateway ready` may never be logged; see Key OpenClaw Internals). Also `systemctl --user show openclaw-gateway -p ExecMainStartTimestamp` is after the pull.
- **Never run `openclaw doctor` when deploying** (Ariel, 2026-10-16: "never run doctor when deploying as its a custom fork"): not with `--fix`, not without it, not as a step of a deploy script, not on a first install. His reason: doctor's other repairs pull the install back toward stock upstream. The one exception is the gateway's own first-start state upgrade, which runs doctor on a shadow copy only (Key OpenClaw Internals): Ariel allowed it for 11.10 alone (2026-11-25: "backup everything, so we can re-enstate anything that got broken. prepare a before/after table of what actually changed"); ask him again at the next schema-changing upgrade. If a release ships another doctor-only migration or advisory that seems to matter, tell Ariel and let him decide.
- **Upgrades that add an identity gate** (11.3 pattern): right after the start, bind the legacy claude-cli crons, clear stale runtime pins and run a live cron test. (1) `openclaw cron edit <id> --model <provider/model>@anthropic:manual --json < /dev/null` for every agentTurn job that runs a Claude model (an unpinned job: its agent's primary; skip jobs pinned to non-Anthropic models and non-agentTurn jobs), then read the result back from `cron_jobs.job_json` → `inferenceBinding` (the CLI hides it). ## Architecture of the Dev Mode Feature

- **Activation**: env only — `OPENCLAW_DEV_MODE=1` in `~/.openclaw/.env`, loaded by `loadDotEnv()` (`src/cli/run-main.ts`) before any command, including `gateway start/restart`. It is the ONLY flag.
- **Why not config**: an early `cli.devMode` key in `openclaw.json` broke the Zod `.strict()` schema when running stock code → gateway crash-loop. A flat `.env` can't be rejected.

## WhatsApp Notes

- **SEC-WA1 mechanism**: stock 9.x+ blocks reasoning on WhatsApp at three points — core drops `isReasoning` payloads unless `replyOptions.reasoningPayloadsEnabled`; `resolveWhatsAppDeliverablePayload` (inbound-dispatch); `isReasoningReplyPayload` (deliver-reply, also matches text starting `Reasoning:`/`Thinking`). Dev-mode opts in and converts before the filters. Core formats reasoning with a "Thinking" preamble (`formatReasoningMessage`, `src/agents/embedded-agent-utils.ts`), which the 7.1 regex (only "Reasoning:") missed, so most reasoning showed WITHOUT 💭. Works for any model that emits reasoning; core emits it only with reasoning level `on` and thinking not `off`.
- **Echo loop lesson**: in self-chat every send echoes back as inbound. 7.x matched echoes by text, SEC-WA1 rewrote the text, and the agent answered its own reasoning forever. 9.x dedupes by message id (`inbound/socket-session.ts` `rememberOutboundMessage`, `inbound/message-normalization.ts` `shouldSkipRecentOutboundEcho`); the fork keeps `echo-guard.ts` as a safety net only.
- **History recorder**: `/root/.openclaw/dev-mode/wa-history.db` (continuous since the kapso era; the running gateway has exactly this file open and the code resolves `$HOME/.openclaw/dev-mode/wa-history.db`, no override). Group names backfilled on connect and updated live. No UI — the sqlite file is the interface.
